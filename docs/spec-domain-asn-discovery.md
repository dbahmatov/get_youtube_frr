# Spec: Domain-Driven ASN Discovery

Статус: **Требования зафиксированы, открытых блокеров нет**
Дата: 2026-07-30

---

## 1. Objective

### Что строим

Заменить ручной список `as_numbers` в `config.yaml` на автоматический конвейер:

```
домены сервиса → резолв с нужной точки → IP → ASN → префиксы → FRR
   (config)         (vantage)        (Cymru)   (RADB/IRR)   (vtysh)
```

Механизм должен работать для **любого** сервиса, описанного в конфиге, без кода под конкретный сервис.

### Зачем

Сейчас ASN вбиты руками. Это ломается, когда:
- сервис добавляет новый ASN или переезжает на другой CDN;
- часть трафика идёт через GGC/edge-кэш, который вообще не в ASN сервиса;
- у сервиса десятки доменов (YouTube: `youtube.com`, `ytimg.com`, `ggpht.com`, `googlevideo.com`, `youtubei.googleapis.com`), и каждый может жить в своём ASN.

### Кто пользователь

Сетевой инженер, который гоняет трафик к сервисам через конкретный аплинк/туннель и держит FRR на роутере. Запуск — cron/systemd-timer, без интерактива.

### Ключевое решение по приоритету (подтверждено заказчиком)

> **Ложноположительный маршрут лучше, чем отсутствующий.**
> **Но и слишком много маршрутов быть не должно.**

> **Суммаризация — только точная. Схлопывать можно лишь то, что схлопывается корректно.**

Третье требование закрывает соблазнительный, но неверный путь: «раз FP допустимы, давайте агрегировать несмежные сети в супернеты». Нет. Анонс адресного пространства, которое нам не принадлежало ни в одном источнике, — это не «чуть шире охват», а выдуманные маршруты, за которые никто не отвечает. Единственная разрешённая агрегация — `ipaddress.collapse_addresses`: объединяются строго смежные сети, дающие ровно тот же набор адресов.

Отсюда следует, где на самом деле решается бюджет: **не после разворота в префиксы, а до него** — на этапе выбора ASN. Число маршрутов регулируется тем, скольким ASN мы разрешаем полный разворот из RADB, а не тем, как агрессивно мы потом их склеиваем (раздел 7a). Допустимые FP живут на уровне «взяли ASN целиком, хотя сервис занимает в нём не всё» — то есть внутри реально анонсируемого этим ASN пространства, а не за его пределами.

Полностью выбрасываем только гарантированно катастрофичное: bogon, RFC1918, default route, префиксы короче `min_prefix_len`.

### Ключевое решение по vantage point (подтверждено заказчиком)

> **Нужно получать GGC и адреса CDN с того хоста, через который направляется трафик.**

Это переворачивает наивную логику «исключить локальный ASN». Наоборот: если провайдерский GGC-кэш отвечает на `*.googlevideo.com`, его префиксы — **валидная цель**, и локальные/провайдерские ASN не фильтруются. Резолв обязан выполняться с той же сетевой позиции (source IP / интерфейс / резолвер), что и продакшн-трафик, иначе ответы CDN будут не те.

## 2. Ответы на архитектурные вопросы (зафиксировано)

| Вопрос | Решение |
|---|---|
| Что анонсировать | **Hybrid**: покрывающие префиксы всегда + полный набор из RADB для ASN, прошедших порог доверия. Настраивается per-service. |
| IP → ASN | **Team Cymru DNS** (`origin.asn.cymru.com`, bulk-режим). Бесплатно, без ключей, без rate-limit. Провайдер за интерфейсом → MaxMind/ipinfo подключаемы позже. |
| Источник доменов | **geosite-категории + ручные seeds/wildcards**, дополняют друг друга. CT-логи, live-пробы, PCAP — вне scope v1. |
| geoip-списки | **И подтверждение ASN, и прямой анонс** (`mode: announce`). |
| Формат списков | **Текстовые, автозагрузка** с пиннингом на релиз и локальным кэшем. Ноль новых зависимостей. |
| GGC / локальный ASN | **Не исключаем.** Резолв с vantage point продакшн-трафика. |
| Суммаризация | **Только точная** (`collapse_addresses`). Приближённая агрегация запрещена. |

## 3. Tech Stack

- Python 3.9+ (текущий минимум из README; CI гоняем и на 3.14, которая стоит локально)
- `pyyaml` — конфиг
- `loguru` — логирование (уже используется)
- `dnspython` — **новая зависимость.** Обязательна: нужен биндинг запросов к source IP, выбор резолвера, работа с CNAME-цепочкой и таймауты. `socket.getaddrinfo` ничего из этого не умеет.
- `pytest` — тесты (уже используется в `tests/`)
- Внешние бинарники: `whois` (RADB), `vtysh` (FRR)

`dnspython` — единственная новая рантайм-зависимость, принята (раздел 12.5). Всё остальное, включая парсеры geosite/geoip и загрузку фидов, обходится стандартной библиотекой. Любая **следующая** зависимость — только с согласования.

## 5. Config schema v2

```yaml
version: 2

router:
  as_number: 65001
  log_file: logs/routes.log
  state_file: state/bgpfeed.json

feeds:                          # глобально: откуда и как тянуть списки
  cache_dir: state/feeds
  refresh_days: 7               # реже не перекачиваем
  offline_ok: true              # нет сети → работаем на кэше, не падаем
  geosite:
    url: "<pinned raw URL>"     # см. раздел 5a, ref фиксируется при реализации
    ref: "202607.01"            # тег релиза или commit sha — НЕ ветка
    sha256: null                # если задан — проверяется, иначе только WARN
  geoip:
    url: "<pinned raw URL>"
    ref: "202607.01"
    sha256: null

defaults:
  strategy: hybrid              # hybrid | asn | covering_prefix

  resolve:
    vantage:
      source_ip: null           # bind DNS-запросов к локальному IP (напр. IP туннеля)
      interface: null           # альтернатива source_ip
      resolvers: [system]       # 'system' = /etc/resolv.conf с этого хоста
    record_types: [A, AAAA]
    rounds: 3                   # несколько проходов: CDN отдаёт разные IP
    round_delay_sec: 2
    concurrency: 20
    timeout_sec: 5
    follow_cname: true

  asn_selection:
    min_ips: 1                  # 1 попадание достаточно (FP лучше пропуска)
    trusted_max_prefixes: 2000  # ASN дороже → covering_prefix вместо полного набора.
                                # Цена считается ПОСЛЕ схлопывания, см. 7b.
                                # По замерам: Google=83, Cloudflare=780, AWS=4902
    exclude_asns: []
    trusted_asns: []
    corroboration: soft         # off | soft | strict
    #   off:    geoip не влияет на выбор ASN
    #   soft:   подтверждённый ASN получает удвоенный trusted_max_prefixes;
    #           неподтверждённый — обычный порог. Никого не отбрасываем
    #   strict: неподтверждённый ASN принудительно limited

  state:
    ttl_days: 90                # долгий TTL: накапливаем картину между прогонами
    keep_manual_forever: true

  guards:
    min_prefix_len: 10          # не анонсируем короче /10 даже после агрегации
    drop_bogons: true           # RFC1918, loopback, link-local, multicast, 0.0.0.0/8
    max_change_ratio: null      # null = не блокировать; 0.5 = отказ при >50% дельте

  budget:
    max_total_prefixes: 20000   # ЖЁСТКИЙ потолок. Калибровано под MikroTik hAP ax3
                                # (1 ГБ RAM, RouterOS 7) — держит с запасом.
                                # Аварийный клапан, а не рабочее ограничение
    per_service_max: null       # опционально: потолок на сервис
    on_overflow: downgrade      # downgrade | fail
    #   downgrade: понижать trusted → limited, пока не влезем (полнота по
    #              наблюдённым IP сохраняется, теряется «запас» по ASN)
    #   fail:      не применять ничего, выйти с ошибкой

services:
  youtube:
    geosite:
      categories: [youtube, googlevideo]
      exclude_domains: []       # точечно выключить лишнее из категории
    geoip:
      categories: [google]
      mode: announce            # announce | corroborate | off
    domains:                    # дополняют geosite, не заменяют
      - youtubei.googleapis.com
    wildcards:
      - pattern: "*.googlevideo.com"
        samples:
          - rr1---sn-4g5e6nz6.googlevideo.com
          - rr2---sn-p2oxu3b-4g0l.googlevideo.com
          - redirector.googlevideo.com
    as_numbers: [36561]         # v1-совместимость: всегда trusted, никогда не истекает
    asn_selection:
      trusted_asns: [36561, 15169, 36040, 43515]

  jetbrains:
    geosite:
      categories: [jetbrains]   # если категории нет — WARN, работаем на domains
    domains: [jetbrains.com, www.jetbrains.com, plugins.jetbrains.com]
    as_numbers: [200019]
```

### Обратная совместимость

Конфиг без `version:` и с одними `as_numbers` читается как v1: сервис работает ровно как сейчас (ASN → RADB → все префиксы), discovery отключён. Существующий `config.yaml` продолжает работать без правок — это hard requirement.

## 5a. geosite и geoip

### geosite — источник доменов

Снимает основную боль: не нужно вести списки доменов руками. `geosite:youtube` уже содержит `youtube.com`, `youtu.be`, `ytimg.com`, `googlevideo.com`, `youtube-nocookie.com`, `yt3.ggpht.com` и далее.

Записи бывают четырёх типов, и годятся нам не все:

| Тип | Пример | Что делаем |
|---|---|---|
| `full:` | `full:www.youtube.com` | Резолвим напрямую |
| `domain:` (дефолт) | `domain:googlevideo.com` | Суффикс, не хостнейм. Резолвим сам суффикс как хост (часто работает: `youtube.com` есть A-запись) + заводим как wildcard-цель для накопления в state |
| `keyword:` | `keyword:youtube` | **Пропускаем**, не резолвится |
| `regexp:` | `regexp:.*\.ytimg\..*` | **Пропускаем** |

Парсер обязан уметь:
- **рекурсивный `include:`** — категории ссылаются друг на друга (`geosite:google` включает подсписки). Нужна защита от циклов: множество уже посещённых категорий;
- **атрибуты** `@cn`, `@ads` и подобные — по умолчанию берём все записи независимо от атрибутов, кроме отфильтрованных `exclude_domains`;
- комментарии `#` и пустые строки.

**Чего geosite НЕ решает:** конкретных хостов `rrN---sn-XXXX.googlevideo.com` там нет и быть не может — только суффикс `domain:googlevideo.com`. Так что `samples` и накопление хостов в state (раздел ниже) остаются обязательны.

Если категории нет в фиде — WARN и работаем на ручных `domains`, не падаем. Это ожидаемая ситуация для нишевых сервисов вроде `jetbrains`.

### geoip — источник префиксов и подтверждение

Работает в двух ролях одновременно (`mode: announce`).

**Роль 1 — прямой анонс.** CIDR из категории идут в итоговый набор наравне с префиксами из RADB. Проходят те же guard-ы (bogon, `min_prefix_len`) и тот же бюджет.

**Роль 2 — подтверждение ASN.** Решает слабое место конвейера: резолв десятка доменов даёт ASN, часть которых мусорная (аналитика, шрифты, сторонние CDN). Сейчас единственный фильтр — размер ASN. Подтверждение добавляет второй, независимый:

> ASN считается **подтверждённым**, если хотя бы один его резолвнутый IP попадает в geoip-категорию этого сервиса.

При `corroboration: soft` (дефолт) подтверждённый ASN получает удвоенный `trusted_max_prefixes` — то есть шире разворачивается. Неподтверждённый судится по обычному порогу. Никого не выбрасываем: это ранжирование доверия, а не фильтр, что соответствует «FP лучше пропуска».

Важно и то, чего geoip **не** покрывает: провайдерский GGC-кэш внутри AS вашего аплинка в `geoip:google` не попадёт никогда — это адреса провайдера, не Google. Ради них и затевался резолв с vantage point. **geoip дополняет конвейер, а не заменяет его**, и отключение резолва в пользу одних лишь списков сломает ваш основной сценарий.

### Взаимодействие с бюджетом

`geoip:google` — порядка тысячи CIDR, это заметная доля бюджета. Поэтому в лестнице понижения (раздел 7a) geoip-категория участвует **наравне с ASN**: при переполнении она может быть понижена `announce → corroborate`, то есть перестать анонсироваться, сохранив роль подтверждения. Ранжируется тем же `prefix_count / len(подтверждённых IP)`.

Отдельно: категории-страны (`geoip:ru`, `geoip:cn`) — это десятки тысяч префиксов. Технически их можно указать, но при загрузке категории размером больше `max_total_prefixes` выдаём громкий WARN: почти наверняка это опечатка в конфиге.

### Доверие к фидам

Список из чужого репозитория, попадающий прямо в BGP-анонс, — это supply chain. Меры:

- **Пиннинг на релиз или commit sha, никогда на ветку.** `ref: main` в конфиге отклоняется валидацией.
- **Локальный кэш** в `state/feeds/`, перекачка не чаще `refresh_days`.
- **`sha256`** проверяется, если задан. Если не задан — WARN при первой загрузке с подсказкой, какой хэш вписать в конфиг.
- **`offline_ok: true`** — нет сети, есть кэш → работаем на кэше. Нет ни того, ни другого → сервис работает на ручных `domains`, а не падает.
- **Guard-ы применяются к geoip-префиксам наравне со всеми.** Bogon, RFC1918, `min_prefix_len`, бюджет. Список не является доверенным источником в обход проверок.
- Смена `ref` в конфиге — обычное изменение, но `plan --diff` покажет дельту маршрутов до применения. Обновлять фид вслепую через `run` не рекомендуется.

Конкретные URL текстовых источников (кандидаты: `v2fly/domain-list-community` для geosite, текстовые публикации geoip от MetaCubeX/Loyalsoldier) фиксируются на этапе реализации — вместе с проверкой, что выбранный ref реально отдаёт нужные категории.

### Проблема wildcard-хостов (решение)

`*.googlevideo.com` неперечислим: хостнеймы вида `rrN---sn-XXXXXXXX.googlevideo.com` генерируются динамически, их фактически бесконечно много. Решение из трёх слоёв:

1. **`samples`** — явный список известных хостнеймов в конфиге, резолвится каждый прогон.
2. **Накопление в state** — хостнеймы, найденные ранее (в т.ч. выгруженные `tools/youtube_probe.py`), хранятся с `last_seen` и переопрашиваются, пока не протухнут по `ttl_days`.
3. **Многораундовый резолв** — `rounds: 3` с задержкой: один и тот же хостнейм у CDN отдаёт разные A-записи, за несколько раундов набирается больше префиксов.

Полнота тут недостижима принципиально — но и не нужна: цель не перечислить все хосты, а накрыть **все ASN и префиксы**, в которых они живут. Их на порядки меньше, и они стабильны.

## 7. Пайплайн: как это работает

```
1. LOAD      config.yaml → валидация, merge defaults в каждый сервис
2. FEEDS     загрузить/взять из кэша geosite и geoip по pinned ref
3. TARGETS   для сервиса собрать хостнеймы:
             geosite (full: + domain:, минус exclude_domains)
             + domains + wildcards[].samples + state.hostnames (не протухшие)
4. RESOLVE   dnspython, bind к vantage.source_ip, N раундов,
             A+AAAA, разворот CNAME → множество IP
5. MAP       IP → ASN через Team Cymru bulk (один запрос на все IP)
6. CORROB    отметить ASN, чьи IP попали в geoip-категорию сервиса
7. FETCH     подтянуть префиксы кандидатных ASN из RADB, СРАЗУ схлопнуть
             каждый набор (кэш в state) → prefix_count = ЭФФЕКТИВНАЯ цена ASN
             в маршрутах, а не число route-объектов. Разница до 40x, см. 7b
8. SELECT    для каждого ASN:
               в exclude_asns              → REJECTED
               в trusted_asns / as_numbers → TRUSTED (не понижается)
               prefix_count <= effective_threshold → TRUSTED
               иначе                       → LIMITED
             порог удваивается для подтверждённых ASN (corroboration: soft)
             effective_threshold подбирается под бюджет (раздел 7a)
9. EXPAND    TRUSTED → все префиксы ASN
             LIMITED → только покрывающий префикс каждого resolved IP
             + geoip-категории с mode: announce
10. GUARD    выкинуть bogon/RFC1918, префиксы короче min_prefix_len
11. SUMMARIZE повторный collapse уже по объединению всех источников:
             схлопывает то, что стало смежным на стыке ASN и geoip
12. DIFF     сравнить с state.announced → to_add / to_remove
13. APPLY    vtysh батчами; при --withdraw снять to_remove
14. PERSIST  записать state: hostnames, IP, ASN, префиксы, ref фидов, timestamps
```

Шаг 5 — сердце решения проблемы «у сервиса куча доменов». Мы не пытаемся угадать, «настоящий» ли это домен сервиса. Мы смотрим на **размер ASN**: если ASN узкий (< 2000 префиксов) — он почти наверняка принадлежит именно этому сервису, берём целиком. Если широкий (AS15169 Google, AS13335 Cloudflare, AS16509 AWS) — берём только те префиксы, где реально живут резолвнутые IP. Это единственное правило, и оно не требует знаний о конкретном сервисе.

## 7a. Бюджет маршрутов

Проблема: `hybrid` по четырём сервисам легко даёт 3000–15000 префиксов (один AS15169 — больше 1400). Это раздувает RIB и замедляет `vtysh`.

Приближённая агрегация как решение **отвергнута заказчиком**: суммаризируем только то, что суммируется корректно. Значит единственный честный рычаг — решать, **скольким ASN мы разрешаем полный разворот**, а не как их потом склеивать.

### Суммаризация: ровно один режим

```python
def summarize(networks: Iterable[IPv4Network]) -> list[IPv4Network]:
    """Точная агрегация. Результат покрывает ровно те же адреса, что и вход."""
    return list(ipaddress.collapse_addresses(networks))
```

Всё. Никаких `min_fill`, супернетов и допусков. `collapse_addresses` объединяет только смежные сети, дающие ровно тот же набор адресов, — проверять его выход на «лишние адреса» бессмысленно, чем и болен текущий `summarize_routes`.

### Бюджет решается на этапе SELECT

Ключевое: `prefix_count` каждого ASN известен **до** разворота — префиксы кандидатных ASN уже подтянуты на шаге FETCH и лежат в кэше. Значит итоговое число маршрутов можно посчитать заранее для любого порога и подобрать порог под бюджет.

```
1. Посчитать план при effective_threshold = trusted_max_prefixes.
2. Влезаем в max_total_prefixes → применить, конец.
3. Не влезаем и on_overflow == fail → выйти с ошибкой, FRR не трогать.
4. Не влезаем и on_overflow == downgrade:
     понижать по одному кандидату, в порядке убывания
     ratio = prefix_count / len(подтверждённых или наблюдённых IP),
     пересчитывая план после каждого понижения, пока не уложимся.
     Кандидаты двух видов, ранжируются в одном списке:
       ASN:             trusted  → limited
       geoip-категория: announce → corroborate
5. Если даже при всех кандидатах в пониженном состоянии не влезли → ошибка.
   Значит бюджет физически недостижим, нужен другой max_total_prefixes.
```

Понижение `trusted → limited` **не теряет наблюдённого покрытия**: все зарезолвленные IP остаются покрыты своими covering-префиксами. Теряется только «запас» — та часть ASN, куда сервис теоретически может переехать, но пока не переехал. Это ровно та точность, которой заказчик готов пожертвовать, и в отличие от супернетов она не выдумывает чужого адресного пространства.

Шаг 5 недостижим на практике: при всех ASN в `limited` число маршрутов ограничено числом различных covering-префиксов среди резолвнутых IP — это десятки, не тысячи. Но обработать его надо явно, иначе получим бесконечный цикл.

### Ранжирование

Порядок жертв детерминирован: первым понижается ASN с худшим `prefix_count / len(seen_ips)` — много маршрутов при малом числе реальных попаданий. Тай-брейк по номеру ASN, чтобы прогон был воспроизводим. `as_numbers`, заданные оператором вручную, из ранжирования исключены и не понижаются никогда.

### Что попадает в лог

```
BUDGET: план 8431 префикс > потолка 5000
  AS16509 (2 IP, 6210 префиксов, ratio 3105) trusted → limited      8431 → 2223
  уложились: 2223 префикса, понижен 1 кандидат из 8
```

Если бюджет не превышен — эта секция в логе не появляется вовсе, и результат идентичен «наивному» прогону.

## 7b. Замеры на реальных данных RADB

Снято 2026-07-30, `whois -h whois.radb.net -- "-i origin AS<N>"`, схлопывание — `ipaddress.collapse_addresses` по уникальным IPv4-сетям.

| ASN | route-объектов | уникальных | **после collapse** | сокращение |
|---|---:|---:|---:|---:|
| AS15169 Google | 3508 | 1831 | **83** | 97.6% |
| AS16509 AWS | 36281 | 25868 | **4902** | 86.5% |
| AS13335 Cloudflare | 7471 | 4275 | **780** | 89.6% |
| AS36040 Google GGC | 694 | 399 | **60** | 91.4% |
| AS200019 JetBrains | 288 | 174 | **97** | 66.3% |
| AS36561 «Main YouTube AS» | 2 | 1 | **1** | — |

### Следствие 1: `prefix_count` считается ПОСЛЕ схлопывания

Это не оптимизация, а исправление ошибки. RADB забит дублями от разных мейнтейнеров и more-specifics под собственными агрегатами; `collapse_addresses` убирает их без потери покрытия. Если мерить ASN сырыми route-объектами, AS15169 (3508 > порога 2000) уедет в `limited` — при реальной цене в **83 маршрута**. Клапан сработает на главном ASN YouTube и обрежет ровно то покрытие, ради которого всё затевалось.

Поэтому `prefix_count` в `select.py` и `budget.py` — всегда **эффективная цена в маршрутах**, то есть длина схлопнутого набора. Схлопывание делается один раз при FETCH и кэшируется в state рядом с префиксами.

**Тест-инвариант:** `prefix_count` для фикстуры AS15169 равен длине схлопнутого набора, а не числу строк `route:`. Прямая защита от возврата этой ошибки.

### Следствие 2: лестница понижения не сработает никогда

При пороге `trusted_max_prefixes: 2000` по эффективной цене: Google, Cloudflare, JetBrains, GGC — все `trusted`. Единственный, кто уходит в `limited`, — AWS с 4902. Суммарно по четырём сервисам конфига выходит порядка 250 маршрутов при бюджете 20000.

Механизм из 7a остаётся, но переходит в разряд страховки на будущее: другой сервис, другой ASN, распухший RADB. Реализуем и покрываем тестами, в проде не ждём.

### Следствие 3: AS36561 в текущем конфиге бесполезен

Подписанный в `config.yaml` как «Main YouTube AS», он даёт **один префикс**: в RADB Google его толком не регистрирует. Всё реальное покрытие YouTube идёт через AS15169, который в конфиг попал как «Google GGC».

То есть текущий инструмент анонсирует не то, что предполагает конфиг, и обнаружить это по самому конфигу невозможно. Прямой аргумент за доменный конвейер и за вывод `show asns`, где видно, сколько маршрутов реально дал каждый ASN.

### Замечание по отладке

Замер RADB воспроизводим откуда угодно — данные не зависят от точки запроса. А вот **резолв доменов и работа с FRR отлаживаются только на `vds-kg`**: в этом весь смысл vantage point, локальная машина даст другие ответы CDN и другой GGC. Тесты сетевых модулей — на фикстурах, живая проверка — на целевом хосте.

## 8. Code Style

Текущий код: `snake_case`, type hints, `dataclass`, f-строки, `loguru`. Сохраняем. Комментарии — по-русски, как сейчас. Что меняем: маленькие чистые функции вместо мегафункций, ошибки через исключения вместо `return []`, никакого `shell=True`.

```python
@dataclass(frozen=True)
class AsnVerdict:
    """Решение по одному ASN: как разворачивать его в префиксы."""
    asn: int
    tier: Literal["trusted", "limited", "rejected"]
    reason: str                    # человекочитаемо, идёт в лог и в `show asns`
    seen_ips: frozenset[str]       # какие резолвнутые IP привели нас к этому ASN


def classify_asn(
    asn: int,
    seen_ips: frozenset[str],
    prefix_count: int,
    policy: AsnPolicy,
) -> AsnVerdict:
    """Решает судьбу ASN. Чистая функция — вся сеть уже отработала выше."""
    if asn in policy.exclude_asns:
        return AsnVerdict(asn, "rejected", "в exclude_asns", seen_ips)

    if asn in policy.trusted_asns:
        return AsnVerdict(asn, "trusted", "явно в trusted_asns", seen_ips)

    if len(seen_ips) < policy.min_ips:
        return AsnVerdict(
            asn, "rejected",
            f"{len(seen_ips)} IP < порога min_ips={policy.min_ips}",
            seen_ips,
        )

    if prefix_count > policy.trusted_max_prefixes:
        return AsnVerdict(
            asn, "limited",
            f"{prefix_count} префиксов > {policy.trusted_max_prefixes}: "
            f"берём только покрывающие",
            seen_ips,
        )

    return AsnVerdict(asn, "trusted", f"узкий ASN ({prefix_count} префиксов)", seen_ips)
```

Правило: сеть и подсчёты — снаружи, решения — в чистых функциях. Так `select.py`, `summarize.py`, `guards.py` тестируются без единого мока.

## 9. Testing Strategy

- **Фреймворк:** pytest. Существующий `tests/test_getroutes.py` переписывается (сейчас не собирается вообще).
- **Расположение:** `tests/`, зеркалит структуру `bgpfeed/`.
- **Сеть в тестах запрещена.** Ответы whois/Cymru — из `tests/fixtures/`. DNS — через мок `dns.resolver`. `vtysh` — через мок `subprocess.run`.
- **Покрытие:** `select.py`, `summarize.py`, `guards.py`, `config.py` — не ниже 90%, это чистая логика и вся цена ошибки там. Остальное — smoke-уровень.

Обязательные кейсы:

| Что проверяем | Почему |
|---|---|
| v1-конфиг (без `version:`) грузится и даёт тот же результат | Регрессия обратной совместимости — hard requirement |
| `collapse` на смежных сетях объединяет, на несмежных — нет | Ядро summarize после переписывания |
| `/0`../7 и bogon-префиксы выкидываются | Единственная реально катастрофичная ошибка |
| Широкий ASN (prefix_count > порога) → `limited` | Защита от заливки всего AWS в FRR |
| Узкий ASN → `trusted` | Основной happy path |
| `as_numbers` из конфига всегда `trusted`, даже если ASN гигантский | Явная воля оператора важнее эвристики |
| Провайдерский/локальный ASN **не** фильтруется | GGC-требование заказчика |
| Протухший по TTL хостнейм выпадает из targets | Иначе state пухнет вечно |
| Ручной ASN не протухает никогда | `keep_manual_forever` |
| Пустой результат резолва не приводит к withdraw всего | Иначе падение DNS = снос всех маршрутов |
| Частичный сбой резолва → анонс не сокращается | То же, мягкий вариант |
| **Суммаризация не расширяет покрытие**: множество адресов до и после совпадает | Главный инвариант. Приближённая агрегация запрещена заказчиком — тест это стережёт |
| Несмежные сети (`10.0.1.0/24`, `10.0.3.0/24`) остаются двумя маршрутами | Явная проверка, что мы не скатились в жадность |
| Превышение бюджета понижает ASN до `limited` и укладывается в потолок | Основной сценарий раздела 7a |
| После понижения все резолвнутые IP по-прежнему покрыты | Понижение теряет запас, но не наблюдённое покрытие |
| Ручные `as_numbers` не понижаются даже при переполнении | Явная воля оператора |
| Подбор порога детерминирован: тот же вход → тот же выход | Иначе каждый прогон = дребезг маршрутов в FRR |
| **`prefix_count` = длина схлопнутого набора, а не число строк `route:`** | Фикстура AS15169: 3508 объектов, цена 83. Считать до схлопывания = понизить главный ASN YouTube |
| Дубли и more-specifics под агрегатом схлопываются в агрегат | Именно этим забит RADB, см. 7b |
| Бюджет недостижим даже при всех кандидатах пониженных → ошибка, не бесконечный цикл | Явная обработка вырожденного случая |
| geosite: `keyword:`/`regexp:` отбрасываются, `full:`/`domain:` берутся | Нерезолвимые записи не должны попадать в цели |
| geosite: рекурсивный `include:` разворачивается, цикл A→B→A не вешает парсер | Категории ссылаются друг на друга |
| Отсутствующая geosite-категория → WARN, работа на ручных `domains` | Нишевые сервисы вроде jetbrains |
| `ref: main` в конфиге фида отклоняется валидацией | Пиннинг только на релиз/sha |
| Нет сети + есть кэш → работаем на кэше; нет ни того ни другого → не падаем | `offline_ok` |
| geoip-префиксы проходят bogon/`min_prefix_len`/бюджет наравне с RADB | Фид не доверенный источник в обход guard-ов |
| geoip-категория понижается `announce → corroborate` при переполнении | Единая лестница для ASN и категорий |

Последние два — критичные. Сценарий «DNS прилёг → discover вернул ноль → diff решил снять все маршруты» кладёт продакшн, и это ровно тот класс аварии, ради которого пишется спека.

## 10. Boundaries

**Always do**
- Прогонять `pytest` перед коммитом
- Валидировать конфиг до любого сетевого запроса
- Логировать обоснование по каждому ASN (`reason` в `AsnVerdict`)
- Ошибку внешнего вызова поднимать исключением, а не глушить `return []`
- Держать v1-конфиг рабочим

**Ask first**
- Добавление зависимостей сверх `dnspython`
- Изменение схемы `state.json` после первого релиза
- Изменение формата команд `vtysh`
- Удаление `youtube_asn_analyzer.py` (пока — переносим, не удаляем)

**Never do**
- `shell=True` с интерполяцией данных из конфига
- Анонсировать bogon, RFC1918 или префиксы короче `min_prefix_len`
- Снимать маршруты по результату неудачного/пустого discover
- **Агрегировать приближённо.** Никаких супернетов, покрытых «достаточно плотно», никакого `min_fill`. Только `collapse_addresses`, только совпадение множества адресов до и после
- Анонсировать адресное пространство, которого не было ни в одном источнике
- Молча превышать `max_total_prefixes`
- Тянуть фид с плавающей ветки вместо пиннинга на релиз/sha
- Пропускать guard-ы для префиксов из geoip на том основании, что «список курируемый»
- Писать секреты или API-токены в конфиг в git
- Материализовывать множества IP-адресов (причина текущей прожорливости `summarize_routes`)

## 11. Success Criteria

1. `python3 -m bgpfeed discover --service youtube` с одной строкой `geosite: {categories: [youtube]}` и **без** ручных `domains` и `as_numbers` находит минимум AS15169 и AS36561, а также ASN локального GGC, если он отвечает на `*.googlevideo.com` с этого vantage point.
1a. Тот же прогон с обрубленной сетью, но живым кэшем фидов даёт тот же список доменов-целей.
2. `python3 -m bgpfeed show asns --service youtube` печатает по каждому ASN: tier, причину, число попавших IP и число префиксов.
3. Существующий `config.yaml` (v1, четыре сервиса, только `as_numbers`) отрабатывает через `python3 -m bgpfeed run --dry-run` и даёт тот же набор префиксов, что текущий `getroutes.py`. Проверяется diff-тестом.
4. ASN с доступными IRR-данными всегда даёт полный набор после точного
   схлопывания независимо от `trusted_max_prefixes`.
4a. `budget.max_total_prefixes` не урезает покрытие: полный схлопнутый набор
   анонсируется и при превышении лимита, с явным WARN в логе.
4b. Суммаризация не меняет множество покрываемых адресов. Проверяется property-тестом на случайных наборах: `set(адреса до) == set(адреса после)` на малых выборках, `subset`-проверка через `subnet_of` на больших — без материализации адресов.
4c. Два прогона подряд на неизменном state дают идентичный набор — никакого дребезга маршрутов в FRR.
5. `run --dry-run --withdraw` печатает точный diff и команды `vtysh`, но не
   меняет FRR.
6. `run --withdraw` синхронизирует все настроенные `network` в локальном
   `router bgp <as_number>`: добавляет отсутствующие и снимает только те,
   которых нет в текущем плане. На первом прогоне это намеренно включает
   маршруты прежнего импортера. Удаление **не срабатывает**, если discover
   завершился с ошибкой или итоговый набор пуст.
7. `pytest tests/ -q` — зелёный (сейчас: не собирается). Покрытие `select/summarize/guards/config` ≥ 90%.
8. Полный `run` по всем четырём сервисам укладывается в 120 секунд на холодном state.
9. README описывает только реально существующие флаги. Проверяется тестом: каждый флаг из README парсится argparse'ом.
10. Ни одного `shell=True` в `bgpfeed/`.

Критерий 9 — прямая реакция на то, что текущий README документирует шесть несуществующих опций.

## 12. Решения по умолчанию

Вопросы ниже закрыты дефолтами. Все обратимы правкой конфига, ни один не блокирует реализацию.

1. **Бюджет — 20000 префиксов.** Целевое железо: MikroTik hAP ax3, 1 ГБ RAM, RouterOS 7. При `trusted_max_prefixes: 2000` в бюджет спокойно влезают все четыре сервиса с полным разворотом узких ASN плюс `geoip:google`. Лестница понижения (7a) в норме не срабатывает вовсе — она аварийный клапан на случай, когда резолв притащит что-то вроде AS16509.
2. **`state.json` не коммитим**, в `.gitignore`. Путь настраивается. Первый прогон на новом роутере даёт неполную картину по wildcard-хостам, дальше накапливается.
3. **IPv6: резолвим AAAA, складываем в state, в FRR не анонсируем.** Данные копятся с первого дня, включение анонса v6 — отдельная задача без миграции.
4. **`youtube_asn_analyzer.py` переезжает в `tools/youtube_probe.py`**, не удаляется. Роль — ручная подпитка state хостнеймами `googlevideo`, которых geosite дать не может. Вне основного конвейера.
5. **`dnspython` принимается как единственная новая рантайм-зависимость.** Без неё нет биндинга к source IP, то есть нет vantage-резолва, то есть не работает основной сценарий с GGC. Текстовые фиды, geosite/geoip-парсеры и всё остальное обходятся стандартной библиотекой.
6. **При недоступности Cymru работаем по последнему известному state**, а не роняем прогон. Соответствует «FP лучше пропуска»: устаревшая карта ASN лучше отсутствия маршрутов. В лог — WARN с возрастом данных.
7. **systemd-юниты кладём в `contrib/`** как пример: `discover` почасово, `apply` раз в сутки. Не устанавливаются автоматически.
8. **`run --withdraw` — reconciliation, как в боевом легаси-юните.** Текущие
   `network` читаются из конфигурации `router bgp <as_number>`, а не из всей
   BGP RIB: learned-маршруты соседей не являются объектами управления.
   Сначала применяются `to_add`, затем `to_remove`. Если добавление не удалось,
   удаление не начинается. Пустой desired-набор всегда ошибка. Решение
   заказчика от 30.07.2026: при первой синхронизации управляемыми считаются
   все `network` внутри AS65004, чтобы убрать старый импорт полностью.
9. **Полное покрытие важнее лимитов (решение заказчика 30.07.2026).** Любая
   обнаруженная или ручная ASN с доступными IRR-данными разворачивается
   целиком после точного `collapse_addresses`. Автоматические переходы
   `trusted → limited` по размеру или бюджету и `geoip announce → corroborate`
   запрещены. `max_total_prefixes` остаётся наблюдаемым порогом для WARN, но
   полный набор анонсируется и сверх 20000. Это решение отменяет прежнюю
   лестницу понижения из разделов 7/7a; явный `exclude_asns`, явная стратегия
   `covering_prefix` и fallback при недоступном IRR остаются.

## 12a. Остаточные Open Questions

Выясняется в ходе реализации, ответы не меняют архитектуру:

1. **Конкретные URL и ref текстовых фидов.** Кандидаты: `v2fly/domain-list-community` для geosite, текстовые публикации geoip от MetaCubeX/Loyalsoldier. Надо проверить, что выбранный релиз реально отдаёт категории `youtube`, `googlevideo`, `google`, и зафиксировать sha256.
2. **Где именно крутится FRR.** hAP ax3 работает под RouterOS, `vtysh` там нет — значит скрипт живёт на отдельной Linux-машине, которая пирится с микротиком по BGP, а микротик уже ставит маршруты. Если топология другая, это меняет только модуль `frr.py`, не конвейер.
3. **Есть ли geosite-категория `jetbrains`.** Если нет — сервис работает на ручных `domains`, это штатный путь с WARN.

## 13. Что НЕ входит в scope v1

- CT-логи (crt.sh), passive DNS, импорт PCAP/DNS-логов — отклонено на этапе вопросов
- Парсинг бинарных `geoip.dat`/`geosite.dat` (protobuf) — только текстовые источники
- sing-box `.srs` и прочие бинарные rule-set форматы
- Live-пробы как плагины конвейера
- Анонс IPv6 в FRR
- Прочие IRR кроме RADB (RIPE, ARIN)
- BGP-коммьюнити, route-map, prefix-list
- Web-UI и метрики/Prometheus
